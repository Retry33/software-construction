# ВышКат

## О проекте

Консольное приложение учёта парка кикшеринга «ВышКат» (Go, DI-контейнер `uber/dig`).

Возможности:
- прием транспорта через обязательный техосмотр;
- учет вещей на балансе (шлемы, док-станции и т.д.);
- отчет: число единиц на балансе и суммарное суточное потребление энергии;
- список техники для новичков;
- вывод наименований и инвентарных номеров всего парка;
- демо-сценарий при запуске.

## Запуск

Требования: Go 1.24+.

```bash
make run
```

При запуске сначала выполняется демо-сценарий, который показывает все возможности приложения: приём транспорта, отказ техосмотра, отклонение некорректных данных,
регистрацию вещей и все отчеты. Затем открывается интерактивное меню.

| Команда | Что делает |
|---|---|
| `make run` | демо-сценарий, затем интерактивное меню |
| `make run-clean` | только интерактивное меню, с пустым парком (флаг `--no-demo`) |
| `make test` | юнит-тесты всех пакетов |
| `make cover` | тесты с покрытием, выводит итоговый процент |
| `make lint` | `gofmt` и `go vet` |
| `make build` | собирает бинарник в `bin/vyshkat` |

Без `make`: `go run ./cmd/vyshkat [--no-demo]`.

### Интерактивное меню

```text
1. Accept a vehicle (with inspection)  — прием транспорта через техосмотр
2. Register an item                    — постановка вещи на баланс
3. Fleet summary                       — число единиц и суточное потребление энергии
4. Vehicles for beginners              — техника для новичков
5. Inventory list                      — наименования и инвентарные номера
6. Run demo scenario                   — повторный запуск демо
0. Exit
```

## Структура проекта

```text
vyshkat/
├── cmd/vyshkat/main.go        — точка входа: сборка контейнера, демо, запуск меню
└── internal/
    ├── domain/                — доменная модель: интерфейсы-возможности, транспорт, вещи
    ├── inspection/            — сервис техосмотра (ServiceCenter)
    ├── fleet/                 — учет парка (Park), порты Inspector и BeginnerPolicy
    ├── console/               — консольный интерфейс и демо-сценарий

```

| Пакет | Ответственность | Зависит от |
|---|---|---|
| `domain` | Что такое транспорт и вещь: интерфейсы `InventoryItem`, `NumberAssigner`, `EnergyConsumer`, `Vehicle`, конкретные типы, value object `Simplicity`, валидация | — |
| `inspection` | Решение о приёмке транспорта в парк | `domain` |
| `fleet` | Прием и учет единиц, выдача инвентарных номеров, отчёты; объявляет интерфейсы `Inspector` и `BeginnerPolicy` | `domain` |
| `console` | Ввод/вывод, меню, демо-сценарий; работает через `io.Reader`/`io.Writer` | `domain`, `fleet` |
| `app` | Связывает реализации с интерфейсами через `uber/dig`, хранит `Config` | все пакеты выше |

## Доменная модель

В модели заведены абстракции для потребителей энергии (док-станции, электроскутеры и т.п.) и для инвентаризуемых объектов. Абстракция для техники позволяет отличать устройства для аренды от док-станций и подобных.

| Интерфейс | Возможность | Кто использует |
|---|---|---|
| `InventoryItem` | имеет наименование и инвентарный номер (`Name`, `Number`) | инвентаризация, отчеты |
| `NumberAssigner` | позволяет один раз назначить инвентарный номер | только `Park` при постановке на баланс |
| `EnergyConsumer` | потребляет энергию (`DailyEnergyKWh`) | отчет по энергии, техосмотр |
| `Vehicle` | прокатная техника с простотой для новичка (`Simplicity`) | прием через техосмотр, правило для новичков |

Велосипед является `Vehicle`, но не реализует интерфейс потребителя энергии, такая абстракция позволяет избежать ненужных методов у некоторых объектов.

Сотрудники в модели не реализуют `InventoryItem`, поэтому поставить их на баланс невозможно уже на уровне типов.

### Встраивание

Общие свойства вынесены в приватные части (`domain/parts.go`), из которых типы собираются встраиванием:

- `inventory` — наименование и инвентарный номер;
- `energyUsage` — суточный расход энергии;
- `rental` — простота для новичка.

```go
type Scooter struct {
    inventory
    energyUsage
    rental
}

type Helmet struct {
    inventory
}
```

### Инвентарные номера

Номер не задается при создании объекта, его выдает `Park` (так как он им и владеет) при постановке на баланс в формате `VK-NNNN`. Номер выдается только при успешной регистрации.

Назначение номера вынесено в отдельный интерфейс `NumberAssigner`: остальной код видит объекты через `InventoryItem` и может номер только читать. Повторное назначение запрещено (`ErrNumberAlreadyAssigned`), так что одна единица не может оказаться на балансе дважды.

### Транспорт и вещи

- Транспорт принимается только через `Park.AcceptVehicle`, который вызывает техосмотр. При отказе единица в парк не попадает.
- Вещи регистрируются через `Park.RegisterItem` без техосмотра. Попытка зарегистрировать через него транспорт отклоняется (`ErrVehicleRequiresInspection`), поэтому обойти техосмотр нельзя.

### Техосмотр и правило для новичков

- `inspection.ServiceCenter` отклоняет транспорт, суточный расход энергии которого превышает лимит из конфигурации.
- Правило для новичков вынесено в стратегию `fleet.BeginnerPolicy`. Реализация по умолчанию — `MinSimplicityPolicy`. Усложнить правило можно новой реализацией интерфейса без изменения `Park`.

## Принципы SOLID

| Принцип | Где в коде | Как применен |
|---|---|---|
| Single Responsibility | `fleet.Park`, `inspection.ServiceCenter`, `console.App`, `app.BuildContainer` | Модель разбита на компоненты, где каждый отвечает за свою задачу. Например, `Park` отвечает за учет, а техосмотр делегирован `ServiceCenter`, ответственность за ввод и вывод берет `console.App`, а `app` отвечает за сборку. Таким образом достигается SRP, так как каждый тип отвечает за свою зону ответственности. |
| Open/Closed | `fleet.BeginnerPolicy`, `console/kinds.go`, части в `domain/parts.go` | Благодаря абстракции `Vehicle`, появляется возможность добавить новое ТС в парк, без переписывания логики `Park`, также есть возможность поменять или усложнить правило выдачи техники новичкам, добавив новую политику, при этом не меняя `Park`. В итоге типы закрыты для изменения, но открыты для расширения. |
| Liskov Substitution | `domain.Vehicle`, `domain.EnergyConsumer`; `Bicycle` без `EnergyConsumer` | Любой `Vehicle` одинаково проходит `AcceptVehicle` и `BeginnerVehicles`. Нет пустых реализаций вроде нулевой энергии у велосипеда. |
| Interface Segregation | `domain/capability.go`: `InventoryItem`, `NumberAssigner`, `EnergyConsumer`, `Vehicle` | Каждый потребитель видит только нужную ему возможность. Логика разбита на интерфейсы потребителей энергии, инвентаризуемых объектов и транспортных средств. |
| Dependency Inversion | `fleet.Inspector`, `fleet.BeginnerPolicy`, `app.BuildContainer` | `Park` зависит от интерфейсов, реализации подставляет контейнер (это позволяет подменять техосмотр в тестах); интерфейс объявлен у потребителя (`fleet`), а не у реализации. |

Наиболее явно выражен `ISP` (`domain/capability.go`), такой выбор обусловлен необходимостью различать объекты по их функциональным и логическим требованиям. Также выражен `DIP`: код зависит от высокоуровневых абстракций, что обеспечивает удобство в unit-тестировании.

Маленькие интерфейсы возможностей несут за собой явную проверку типов в рантайме, однако в данном случае для трех отчетов строить полиморфный вызов было бы излишним усложнением бизнес-логики.

Важно отметить, что `console.App` зависит от конкретного `*fleet.Park`, без интерфейса. Это формально нарушает (ограничивает) `DIP` в этом месте, но в данном случае решение принято намеренно, так как `Park` всего один (второй реализации парка нет) и городить лишние абстракции спровоцировало бы мертвый `SOLID`.

## DI-контейнер

Используется `uber/dig`. Все зависимости собираются в одном месте — `app.BuildContainer`, `main` только вызывает приложение через `Invoke`.

| Зависимость | Что подставляется | Зачем |
|---|---|---|
| `fleet.Inspector` | `inspection.ServiceCenter` | техосмотр подменяется без изменения `Park` |
| `fleet.BeginnerPolicy` | `fleet.MinSimplicityPolicy` | правило для новичков задается снаружи |
| `app.Config` | лимит техосмотра, порог простоты | правила настраиваются без правки кода |
| `app.IO` | `io.Reader` / `io.Writer` | консоль тестируется на строках, а не на реальном терминале |
| `*fleet.Park` | один экземпляр на контейнер | демо и интерактивное меню работают с одним парком |

Подмена техосмотра в контейнере — через `c.Decorate` (`TestContainerInspectorCanBeReplaced`).

## Тестирование

```bash
make test
make cover
```

| Пакет | Покрытие |
|---|---|
| `domain` | 81.4% |
| `fleet` | 95.5% |
| `inspection` | 100% |
| `console` | 91.7% |
| `app` | _(см. `make cover`)_ |

Тестовые двойники:
- `fakeInspector` — техосмотр с заданным ответом (принять / отклонить);
- `stubPolicy` — правило для новичков, пропускающее всех или никого;
- `rejectAll` — техосмотр, подставляемый в DI-контейнер вместо `ServiceCenter`.

Решение техосмотра фиксируют:
- `TestAcceptVehicleApproved`, `TestAcceptVehicleRejected` (`fleet/park_test.go`) — подмена через конструктор `NewPark`;
- `TestContainerInspectorCanBeReplaced` (`app/container_test.go`) — подмена в DI-контейнере;
- `TestServiceCenterInspect` (`inspection/service_center_test.go`) — само правило техосмотра;
- `TestRegisterItemSkipsInspection` — вещи регистрируются без техосмотра (инспектор падает при любом вызове).

Правило «для новичков» фиксируют `TestBeginnerVehiclesDefaultRule` (порог 6) и `TestBeginnerVehiclesCustomPolicy` (со `stubPolicy`).

## Расширение

| Что добавляем | Что меняется | Что не меняется |
|---|---|---|
| Новый вид транспорта (например, гироскутер) | новый тип в `domain`, собранный из частей; строка в `console/kinds.go` | `Park`, `ServiceCenter`, отчеты, тесты |
| Сотрудник | отдельный пакет; не реализует `InventoryItem`, поэтому на баланс не попадает | `domain`, `fleet` |
| Склад запчастей | запчасть — `InventoryItem`; новый пакет со своим учетом | `domain` |

Что сломается: счетчик инвентарных номеров живет внутри `Park`. Если номера должны быть общими для парка и склада, выдачу номеров придется вынести в отдельную зависимость.
